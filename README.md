# hanji

*[English](README.en.md)*

한글(HWP·HWPX), PDF, 이미지, 영상을 **이 기기 안에서** 열고 바꾸고 인쇄합니다. Windows와
macOS용 데스크톱 앱으로 쓰거나, 브라우저 탭에서 바로 씁니다.

온라인 변환 사이트는 파일을 서버로 올린 다음 지우겠다고 약속합니다. 이 도구는 지울 것이
없습니다. 애초에 보내지 않기 때문입니다. 화면에는 바깥으로 나간 요청 수를 실시간으로 세는
배지가 붙어 있어서, 주장이 아니라 눈으로 확인할 수 있습니다. 종단 테스트는 요청이 한 건이라도
나가면 빌드를 실패시킵니다.

> 아직 초기 버전입니다. 뷰어와 변환, 인쇄는 동작합니다. 남은 계획은 아래 로드맵에 있습니다.

## 설치

처음 쓰신다면 [docs/GUIDE.ko.md](docs/GUIDE.ko.md)를 보세요. 설치부터 저장까지 5분이면 됩니다.

| | |
|---|---|
| **Windows** | [Releases](../../releases)에서 `-setup.exe`를 받아 실행합니다 |
| **macOS** | [Releases](../../releases)에서 `-universal.dmg`를 받아 응용 프로그램으로 끌어다 놓고, **첫 실행만 우클릭 후 열기**를 누릅니다 |
| **브라우저** | 설치 없는 웹 버전은 준비 중입니다. 기능은 같고 주소만 아직 공개 전입니다 |

macOS 빌드에는 코드 서명이 없습니다. Apple 개발자 인증서가 연 99달러인데 이건 무료 도구라
아직 넣지 않았습니다. 그래서 첫 실행에만 우클릭 후 열기가 필요합니다. Windows도 같은 이유로
SmartScreen 안내가 뜹니다. 숨기지 않고 적어 두는 이유는, 프라이버시 도구가 신뢰를 잃는 순간이
바로 첫 실행에서 뜨는 경고 창이기 때문입니다.

## 쓰는 법

**동작은 하나입니다. 창 위로 파일을 끌어다 놓으세요.** 창 전체가 목표라 조준할 작은 상자가
없습니다. 문서가 열리면 그 위에 인쇄와 변환 버튼이 나타납니다.

![끌어다 놓기, 열림, HWPX로 저장까지 15초](docs/media/demo.gif)

이 클립은 손으로 녹화한 것이 아니라 [`demo-record.py`](demo-record.py)가 만듭니다. 실제 앱을
실제 드롭 이벤트와 실제 변환으로 통과시키기 때문에, 끌어다 놓기나 HWPX 내보내기가 망가지면
데모도 같이 망가집니다. 이미 멈춘 기능을 계속 광고하는 일이 생기지 않습니다.

### 인쇄

문서를 열면 **인쇄** 버튼이 저장 형식 왼쪽에 있습니다. 공공기관 업무에서 변환의 종착지는 대개
종이입니다. 결재를 받든 철을 하든 마지막 단계는 출력이라, 인쇄가 빠지면 결국 다른 프로그램을
한 번 더 거쳐야 합니다.

화면에 보이는 페이지가 그대로 나갑니다. 도구 막대와 상태 줄, 배지는 종이에 찍히지 않습니다.
한 쪽이 한 장으로 나가고, 마지막 장 뒤에 빈 종이가 딸려 나오지 않습니다. 테스트가 실제로
인쇄를 실행해 나온 쪽수를 세기 때문에, 스크롤된 화면 한 장만 나오는 흔한 실패는 빌드에서
걸립니다.

데스크톱 앱은 `window.print()`를 쓰지 않고 셸의 네이티브 인쇄를 부릅니다. macOS의 웹 뷰에서는
`window.print()`가 아무 일도 하지 않고 조용히 끝날 수 있는데, 눌러도 반응이 없는 인쇄 버튼은
없는 것보다 나쁩니다. 사용자가 문서를 탓하게 되기 때문입니다.

## 왜 만들었나

한국 사람의 문서 폴더에는 HWP와 PDF와 이미지가 섞여 있는데, 업로드 없이 이 셋을 다 다루는
도구가 없었습니다. 훌륭한 클라이언트 사이드 도구들은 하나같이 한 형식만 봅니다. 이미지는
Squoosh, PDF는 BentoPDF와 PDFCraft, 한글은 rhwp입니다.

그사이 공공기관은 2026년 5월 18일부터 개방형 문서 형식(HWPX·ODF·PDF/A)으로 옮기게 됐습니다.
한글 형식을 다루는 도구가 갑자기 많은 사람의 일이 된 셈입니다.

## 지금 되는 것

| | |
|---|---|
| 보기 | HWP, HWPX, HML, PDF, 이미지, 영상(MP4·MOV·WebM) |
| 인쇄 | 한글 문서, PDF, 이미지 |
| 변환 | HWP ↔ HWPX ↔ HML · 한글 → PDF/PNG · PDF → PNG/JPEG · 이미지 → PNG/JPEG/WebP |
| 편집 | PDF 쪽 나누기, 회전, 원하는 쪽만 남기기, 합치기 |
| 만들기 | 영상 → 스틸 또는 GIF · 이미지 → GIF 또는 PDF |

여러 파일을 한 번에 놓으면 "이 문서에 뭐가 들었나"에서 "이걸로 하나를 만들자"로 바뀝니다. PDF를
합치거나, 사진을 GIF나 PDF로 묶습니다. 순서는 끌어 놓은 순서가 아니라 파일 이름을 따릅니다.
여러 파일을 한꺼번에 놓으면 운영체제가 정한 순서가 넘어오는데, 그 순서는 사용자에게 보이지
않기 때문입니다.

GIF는 그냥 이어 붙이는 대신 쓰임새별 프리셋을 고르게 했습니다. 슬라이드쇼, 부메랑, 한 번만
재생, 표지 강조, 대화용 소형 같은 것들입니다. 누르면 바로 그 설정으로 변환됩니다.

**특히 HWP에서 HWPX로 바꾸는 기능을 짚어 두고 싶습니다.** 공공기관이 옮겨야 하는 그 개방형
형식이 HWPX입니다. 엔진이 HWPX를 직접 내보내기 때문에 다시 그린 결과가 아니라 진짜 HWPX
꾸러미가 나옵니다. 그리고 이걸 해주는 다른 변환기들과 달리, 파일이 탭 밖으로 나가지 않습니다.
테스트는 문서를 변환한 뒤 결과를 다시 열어서 쪽 배치가 살아남았는지까지 확인합니다.

여러 쪽을 내보내면 `.zip`으로 묶입니다. 압축 없이 담기만 하는 작은 ZIP 작성기를 씁니다. 안에
들어가는 PNG와 JPEG가 이미 압축된 데이터라, 한 번 더 압축해 봐야 CPU만 쓰고 크기는 그대로이기
때문입니다.

PDF로 내보내면 각 쪽이 이미지가 되어 글자를 선택하거나 검색할 수 없습니다. 버튼에 그렇게 적어
두었습니다. 글자를 살리려면 한글 폰트를 PDF에 심어야 하는데, 그건 제대로 된 작업량이라 없는
척하지 않고 로드맵에 넣었습니다.

실제 2쪽짜리 한국 공무원 시험지로 재보면 HWP 파싱이 처음에 50밀리초 남짓, 두 번째부터는
5밀리초입니다. 첫 화면 무게는 gzip 기준 5KB 아래입니다. 엔진은 전부 동적 임포트라 그 형식의
파일을 실제로 열 때만 내려받습니다.

## 한글이 제대로 보이는가

두 단 짜리 한글 문서가 한동안 이상하게 그려졌습니다. 원인은 두 개였고 둘 다 밝혔습니다.

첫 번째는 우리 잘못이었습니다. `@rhwp/core`는 페이지가 `globalThis.measureTextWidth` 콜백을
제공해야 합니다. WASM은 브라우저 폰트를 볼 수 없어서 줄바꿈을 정하려면 이걸 물어봐야 합니다.
그걸 안 걸어 둬서 글자 폭이 잘못 측정되고 단이 넘쳤습니다. 고쳤습니다.

두 번째는 상류 회귀였습니다. rhwp 커밋 `10c36e23`에서 들어왔고 v0.7.6부터 배포됐습니다. 표
앞에 탭이 있으면 그 탭 폭만큼 표가 오른쪽으로 밀려서, 테두리 친 문단이 단을 벗어납니다.
브라우저 없이 rhwp 자체 CLI에서도 그대로 재현됩니다.

v0.7.6 이후 배포된 모든 `@rhwp/core`에 있어서 올려 붙일 버전이 없었습니다. 그래서 한 파일짜리
패치를 만들어 엔진을 직접 빌드해 씁니다. 출처와 재빌드 절차는
[vendor/README.md](vendor/README.md)에, 어느 커밋에서 들어왔는지 되짚은 과정과 측정치는
[docs/DECISIONS.md](docs/DECISIONS.md)에 있습니다. 패치를 얹은 상태로 상류 테스트 2933개가
전부 통과합니다.

`e2e-smoke.py`가 어떤 표도 페이지 폭을 넘지 않는지 확인합니다. 회귀가 다시 들어오면 조용히
잘못 그려지는 대신 빌드가 실패합니다. 이 검사는 `<defs>` 안의 클립 패스를 빼고 실제로 그려지는
사각형만 잽니다. 안 그리면 화면에 보이지도 않는 요소를 두고 표가 삐져나갔다고 오판합니다.

한컴의 렌더러를 기준으로 삼을 수는 없으니, 여기서 "맞다"는 뜻은 *회귀 이전의 rhwp와 같고
페이지 안에 있다*는 것입니다. 한글 문서의 진짜 정확도 기준 자료를 만드는 일은 로드맵에 있습니다.

## 안 보낸다는 걸 어떻게 믿나

믿지 마시고 확인하세요. 세 가지 방법이 있습니다.

**배지를 보세요.** 창 오른쪽 위에 바깥으로 나간 요청 수가 있습니다. 쓰는 동안 계속 0이어야
합니다. 이건 문구가 아니라 `fetch`와 `XMLHttpRequest`와 비콘을 전부 가로채서 세는 계기입니다.

**의존성 목록을 보세요.** [`src-tauri/Cargo.toml`](src-tauri/Cargo.toml)에 HTTP 클라이언트가
없습니다. 파일을 보낼 코드 자체가 없는 것이 "보내지 않는다"의 가장 강한 형태입니다. 전부 읽는
데 1분이 안 걸릴 만큼 짧습니다.

**인터넷을 끊고 쓰세요.** 설치한 뒤에는 네트워크 없이 그대로 동작합니다.

테스트도 배지를 믿지 않습니다. 브라우저가 보낸 모든 요청을 직접 기록해서 우리 출처 밖으로 나간
것이 하나라도 있으면 실패시킵니다.

## 데스크톱

데스크톱 앱은 웹사이트가 내려주는 것과 같은 번들을 감싼 [Tauri v2](https://tauri.app) 셸입니다.
이식한 것이 아닙니다. 파서와 렌더러와 인코더가 전부 같은 코드입니다. 원래부터 로컬에서 돌고
있었기 때문에 다른 것은 셸뿐입니다.

그 셸은 일부러 거의 비워 뒀습니다. `src-tauri/`는 Rust 40줄 남짓이고, 의존성에 HTTP 클라이언트가
아예 없습니다. 셸이 소유한 것은 세 가지뿐입니다. 네이티브 저장 창을 띄우고, 고른 경로에 바이트를
쓰고, 시스템 인쇄를 부르는 것입니다.

브라우저 탭과 네이티브 창 사이에 진짜로 다른 것이 셋 있고, 각각 임시방편이 아니라 제대로 손봐야
했습니다.

**끌어다 놓기.** Tauri의 웹 뷰가 페이지보다 먼저 파일 드롭을 가로채서, HTML5 `drop` 이벤트가
아예 발생하지 않습니다. 앱에서 가장 중요한 동작이 조용히 아무 일도 안 하게 됩니다.
`dragDropEnabled: false`로 가로채기를 꺼서 두 셸이 같은 코드를 쓰게 했습니다.

**저장.** 웹은 blob URL과 가짜 앵커 클릭으로 파일을 씁니다. macOS 웹 뷰에는 그걸 받아 줄 다운로드
관리자가 없어서 데스크톱은 네이티브 저장 창을 씁니다. 그 창에는 브라우저에 없는 상태가 하나
생깁니다. **취소**입니다. 그래서 `saveBlob`은 바이트가 실제로 쓰였는지를 돌려줍니다. 취소된
대화상자 위에 "저장됨"을 띄우는 것은, 하필 사용자가 이 도구가 말한 대로 하는지 확인하는 그
순간에 하는 작은 거짓말입니다.

**권한.** 이 창이 시스템에 요청할 수 있는 것은 저장 창을 띄우는 것과 `$HOME` 안에 쓰는 것이
전부입니다([`src-tauri/capabilities/default.json`](src-tauri/capabilities/default.json)). 네트워크도
셸도 임의 파일 접근도 없습니다. 그 파일에 없는 것은 의존성이 시도하더라도 프런트엔드에서 닿지
않습니다.

Windows와 macOS 번들은 서로 교차 빌드가 안 되므로
[`.github/workflows/release.yml`](.github/workflows/release.yml)이 각각 자기 러너에서 빌드합니다.
macOS는 인텔용과 애플 실리콘용을 나누지 않고 유니버설 바이너리 하나로 냅니다. 자기 맥이
어느 쪽인지 알아야 할 이유가 없기 때문입니다.

## 보안

네 가지를 묻고, 각 질문에는 그 분야에서 통용되는 도구로 답합니다. 커밋 기록에 비밀값이 있는가,
의존성에 알려진 취약점이 있는가, 코드에 알려진 위험 패턴이 있는가, 라이선스 의무를 어기고 있는가.

```bash
tools/security-scan.sh          # 있는 도구로 전부
tools/security-scan.sh deps     # 한 항목만
```

CI에서는 [`.github/workflows/security.yml`](.github/workflows/security.yml)이 gitleaks, npm audit,
cargo audit, osv-scanner, CodeQL, semgrep을 돌립니다. 주 단위 스케줄도 걸려 있습니다. 의존성은
코드를 안 고쳐도 취약해집니다. 정확히는 누군가 취약점을 공개하는 순간 취약해집니다.

이 검사는 이미 값을 했습니다. pdf.js 5.6.83부터 6.2.107까지에 **조작된 PDF를 여는 것만으로 임의
JavaScript가 실행되는** 결함(GHSA-hq66-cqwq-w95j)이 있었고, 의존성 감사가 그걸 잡았습니다.
문서 뷰어에게는 이게 위협 모델 전체입니다. 6.2.108로 올렸습니다.

## 라이선스

hanji가 직접 쓴 소스는 MIT입니다. 다만 배포물에는 다른 라이선스를 가진 구성 요소가 함께
들어갑니다. pdf.js는 Apache-2.0이고, 본문에 쓰는 Noto 글꼴은 SIL 오픈 폰트 라이선스이며, Tauri가
끌어오는 크레이트 중 다섯 개는 MPL-2.0입니다. "hanji는 MIT"는 이 저장소를 설명하는 말이지
설치 파일 안에 든 모든 것을 설명하는 말이 아닙니다.

전체 목록과 라이선스 전문은 [THIRD_PARTY_LICENSES.md](THIRD_PARTY_LICENSES.md)에 있습니다. 손으로
쓰지 않고 실제 설치된 패키지에서 생성합니다.

```bash
python3 tools/license-report.py            # 고지 파일 다시 생성
python3 tools/license-report.py --check    # 문제되는 라이선스가 있으면 실패
```

MPL-2.0은 파일 단위 카피레프트라 더 큰 저작물 안에서 다른 조건으로 배포할 수 있고, 대신 해당
파일들은 그 라이선스를 유지하고 소스를 계속 구할 수 있어야 합니다. 다섯 개 모두 손대지 않은
공개 릴리스 그대로 쓰고, 어디서 구할 수 있는지 고지 파일에 적어 두었습니다.

`--check`는 MPL 때문에는 실패하지 않습니다. 기록하면 되는 일로 빌드를 깨면 모두가 검사를
건너뛰는 법을 배우게 됩니다. GPL이나 AGPL처럼 이 프로젝트의 성격을 바꾸는 것이 들어올 때만
실패합니다. 지금은 하나도 없습니다.

## 개발

```bash
npm install
npm run dev            # 웹, http://localhost:5173
npm run build          # 타입 검사 + 프로덕션 빌드
npm run desktop:dev    # 네이티브 창, 같은 프런트엔드를 핫 리로드
npm run desktop:build  # .dmg / .exe 를 src-tauri/target/release/bundle 에
```

데스크톱 빌드에는 [Rust 툴체인](https://rustup.rs)이 필요합니다. 웹 빌드는 필요 없습니다.

종단 테스트는 실제 Chromium으로 프로덕션 빌드를 몰아서 화면에 나타난 것을 확인합니다. 바깥으로
아무것도 안 나간다는 주장도 배지의 자기 보고가 아니라 요청을 직접 기록해서 확인합니다. 가지고
계신 문서 아무거나 두 개를 물려 주세요.

```bash
export HANJI_FIXTURE_HWP=/경로/아무.hwp
export HANJI_FIXTURE_PDF=/경로/아무.pdf
npm run preview &      # :4173이 이미 쓰이면 HANJI_URL로 주소를 바꿉니다
python3 e2e-smoke.py
```

테스트용 파일은 커밋하지 않고 그때그때 물려 줍니다. 쪽수는 하드코딩하지 않고 넣어 주신 문서에서
읽습니다. 그래서 "한 쪽에 PNG 하나"가 실제로 렌더된 쪽수에 대해 검사됩니다.

개발 서버는 프로덕션과 같은 COOP/COEP 헤더를 보냅니다. 교차 출처 격리 문제가 배포 후가 아니라
로컬에서 드러나게 하기 위해서입니다.

## 배포

Cloudflare Pages를 씁니다. 빌드 명령은 `npm run build`, 출력 디렉터리는 `dist`입니다. CSP와
COOP/COEP 설정은 `public/_headers`에 있습니다.

```bash
npx wrangler pages deploy dist --project-name hanji
```

**GitHub Pages를 안 쓰는 이유**는 예상하실 만한 것과 다릅니다. 이 앱은 응답 헤더가 하나도 없어도
잘 돕니다. 스레드를 쓰는 곳이 없어서 교차 출처 격리가 아예 상관없습니다(측정했습니다,
[docs/DECISIONS.md](docs/DECISIONS.md) D1). 이유는 대역폭과 프레이밍입니다. 한글 문서 하나를
열면 6MB 정도가 오가서 월 100GB면 1만 7천 세션쯤입니다. 그리고 진짜 CSP 헤더가 없으면
`frame-ancestors`를 잃는데, 그러면 누구든 이 도구를 자기 페이지 안에 끼워 넣고 "여기 올리면
변환해 드립니다"라고 할 수 있습니다. Cloudflare Pages는 대역폭을 재지도 않고 헤더도 보냅니다.

## 언어

한국어가 기본이고 머리말에 English 전환 버튼이 있습니다. `navigator.language`를 보지 않고 무조건
한국어로 시작합니다. 이 도구는 한글 문서를 위해 있고, 영어 브라우저로 들어온 사람은 HWP 파일을
들고 있는 영어 사용자보다 영어 환경을 쓰는 한국인일 가능성이 큽니다. 이 방향으로 잘못 짐작하면
정작 이걸 만든 대상에게 제품이 숨습니다. 고른 언어는 저장되고, 전환하면 페이지를 새로 고치는
대신 열려 있던 문서를 다시 엽니다.

## 화면 테마

시스템, 밝게, 어둡게 세 가지입니다. 두 가지가 아닙니다. 토글 하나짜리는 실수로 한 번 누르면
운영체제 설정을 영영 덮어쓰고 "그냥 내 기계를 따라가"로 돌아갈 방법이 없는데, 대부분의 사람이
원하는 건 그쪽입니다. 고른 값은 저장되고, 명시적으로 고른 값은 *양쪽 모두에서* 이깁니다. 밝은
운영체제에서 어둡게 쓰는 경우까지 포함해서인데, 이건 `prefers-color-scheme`만으로는 표현할 수
없습니다.

저장된 테마는 모듈 번들이 아니라 `<head>`의 별도 동일 출처 스크립트가 적용합니다. 로드할 때
잘못된 색이 한 번 번쩍이지 않게 하려는 것입니다. 인라인 `<script>`가 아니라 파일인 이유는 CSP가
`script-src`를 `'self'`로 묶어 두었기 때문입니다.

어두운 테마에서도 문서 쪽은 흰 종이 그대로입니다. 그 지면은 사용자의 내용이고, 색을 바꾸면
문서를 잘못 전달하게 됩니다. 미리보기와 Acrobat도 같은 선택을 합니다.

## 반응형

320, 375, 768, 1024, 1440에서 실제 터치 에뮬레이션으로 확인합니다. 어느 폭에서도 가로 스크롤이
없고, 포인터가 손가락인 환경에서는 모든 조작 대상이 44px을 넘습니다. 데스크톱 도구 막대는
일부러 촘촘하게 두고, `(pointer: coarse)`에서만 커집니다.

머리말은 고정 높이 한 줄이 아니라 줄바꿈합니다. 터치 대상을 44px로 올렸더니 320px에서 한 줄에
안 들어가 37px이 넘쳤는데, 대상을 다시 줄이는 대신 원인을 고쳤습니다.

## ffmpeg를 안 넣은 이유

스틸 한 장 뽑기와 짧은 GIF 만들기는 사람들이 영상 도구를 원하지 않으면서 영상 도구에 바라는 두
가지인데, 둘 다 우리 코덱이 필요 없습니다. `<video>` 요소를 캔버스에 그리면 플랫폼이 이미 재생할
수 있는 것에서 프레임이 나옵니다. 이 앱이 도는 모든 환경에서 MP4/H.264와 WebM이 그렇습니다. GIF
인코딩은 `gifenc`인데 gzip 10KB 정도이고 지연 로드합니다.

ffmpeg를 싣는 쪽이 뻔한 대안이었고 측정해 보고 접었습니다. 앱 전체가 9.3MB인데 정적 ffmpeg는
70에서 90MB입니다. 제품 전체의 열 배쯤 됩니다. 흔한 빌드는 `--enable-gpl --enable-libx264`로
구성돼 있어서, MIT 코드가 GPL이 되지는 않지만 배포하는 번들에 GPL 의무가 붙습니다. 그리고 긴밀히
붙은 사이드카가 단순 병합인지 아닌지는 다툼이 있는 영역이라, 1인 메인테이너가 자원할 자리는
아닙니다. 무엇보다 "의존성 목록을 보세요, 네트워크 클라이언트가 없습니다"가 핵심 주장인
프로젝트가 컨테이너와 코덱 파서 수백 개를 대신 책임지고 싶지는 않습니다.

이 선택의 정직한 대가는 이렇습니다. 특이한 코덱은 안 열리고, 자르기도 재인코딩도 오디오도
없습니다. 그건 영상 편집기가 할 일이고 이건 영상 편집기가 아닙니다.

## 한글 조판

브라우저는 한글을 중국어나 일본어처럼 다뤄서 어느 음절 사이에서든 줄을 끊습니다. 그래서 처음
배포한 화면의 첫 문장이 `문서를 끌어다 놓으세 / 요.`로 나왔습니다. 제품의 첫 화면에서 단어가
반으로 갈린 것입니다. `:lang(ko) { word-break: keep-all }`이 띄어쓰기에서만 끊게 만듭니다. 한국어를
실제로 조판하는 방식입니다. `overflow-wrap: break-word`와 같이 써서 상태 줄의 긴 파일 이름처럼
공백 없는 긴 토큰은 넘치는 대신 줄바꿈되게 했습니다.

## 접근성

키보드 순서는 열기, 각 변환, 파일 입력 순입니다. 모든 조작 대상이 진짜 `<button>`이고 초점
표시가 보입니다. 상태 줄은 `aria-live` 영역이고, 변환이 끝나면 초점이 `<body>`로 떨어지지 않고
누른 버튼으로 돌아옵니다. 움직임은 `prefers-reduced-motion`을 따릅니다.
