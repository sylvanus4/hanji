# 로컬 문서 스튜디오 — 뷰어 + 변환기 계획서

작성 2026-08-06. 근거: 병렬 리서치 4건 + 로컬 실증 측정.
한 줄 정의: **파일이 절대 업로드되지 않는, 브라우저에서 도는 문서 뷰어 겸 변환기.**

---

## 1. 리서치가 확정한 것

### 1.1 호스팅은 GitHub Pages가 아니라 Cloudflare Pages다

GitHub Pages는 **커스텀 HTTP 응답 헤더를 설정하는 수단이 아예 없다**(공식 문서 + 커뮤니티
이슈 3건, 장기 미해결). COOP/COEP를 못 주면 `SharedArrayBuffer`가 막히고, 그러면 멀티스레드
WASM(영상·오디오 코덱, LibreOffice WASM)이 전부 막힌다. 우회책 `coi-serviceworker`는 첫 방문
시 강제 새로고침이 필요하고 Safari 16.5에서 깨진 전례가 있으며, COEP를 켜는 순간 외부 폰트·
분석 스크립트 같은 크로스오리진 리소스가 조용히 차단된다.

| 호스트 | 대역폭(무료) | 커스텀 헤더 | 비고 |
|---|---|---|---|
| GitHub Pages | 100GB/월(soft) | **불가** | 사이트 1GB 상한 |
| **Cloudflare Pages** | 실질 무제한 | **가능**(`_headers`) | 에셋 25MiB/개, 상업이용 가능 |
| Netlify | 약 15GB/월(2025-09 개편) | 가능 | 무료 대역폭 최소 |
| Vercel Hobby | 100GB/월 | 가능 | **상업 이용 금지** |

→ **Cloudflare Pages 확정.** 클라이언트 처리라 대역폭은 앱 번들만 나가고 사용자 파일은 0이다.

### 1.2 진짜 병목은 호스팅이 아니라 iOS Safari 메모리다

iPhone Safari는 워킹셋 약 100MB, iPad 약 200MB 부근에서 탭이 죽는다. WASM 32비트 주소공간은
4GB 상한이고, Memory64는 WebAssembly 3.0(2026-06-13 확정)에 들어갔지만 **Safari 미지원**에
성능도 10~100% 느리다. 즉 대용량 파일은 `Blob.stream()` 청크 처리가 필수고, 모바일에서는
파일 크기 가드를 UI에 넣어야 한다. GitHub Pages의 1GB/100GB 수치는 우리 앱 번들 얘기지
사용자 파일과는 무관하다.

### 1.3 범용 PDF 툴킷 자리는 이미 찼다

| 프로젝트 | ★ | 생성 | 성격 |
|---|---|---|---|
| Stirling-PDF | 88,982 | — | 셀프호스팅 서버(브라우저 전용 아님) |
| Squoosh | 25,622 | — | 이미지, 클라이언트, Google |
| **BentoPDF** | 14,529 | 2025-10 | PDF 100+ 도구, 100% 브라우저 |
| **PDFCraft** | 8,168 | 2026-01 | PDF 90+ 도구, WASM |

BentoPDF·PDFCraft 둘 다 1년 안에 8천~1.4만 스타. 카테고리가 뜨겁다는 증거인 동시에,
"프라이버시 우선 범용 PDF 툴킷"은 이미 두 곳이 점유했다는 뜻이다. 세 번째로 같은 걸
만드는 건 의미가 없다.

동시에 이건 **포지셔닝이 통한다는 증명**이기도 하다. iLovePDF·Smallpdf·CloudConvert·Convertio는
전부 서버 업로드형이고(각사 프라이버시 페이지로 확인), "빨리 지웁니다"를 판다. "애초에 안
올라갑니다"는 구조적으로 그들이 못 따라오는 자리다.

### 1.4 Office → PDF는 깨끗한 방법이 없다

LibreOffice WASM(ZetaOffice)은 실제로 동작하지만 COOP/COEP 필수에 초기 다운로드 약 50MB
(3자 보고, 벤더 미공개), 모바일은 공식 데모가 스스로 비활성화한다. mammoth.js 계열은
머리글·바닥글을 아예 렌더하지 않고, html2canvas 경로는 텍스트가 래스터라이즈돼 선택·검색이
안 된다. pptx는 무료 클라이언트 변환 경로가 사실상 없다. xlsx만 SheetJS(Apache-2.0)로 해결되나
npm 배포가 끊겨 자체 CDN에서 받아야 한다.

→ **Office는 v1 범위에서 뺀다.** 넣더라도 "보기 전용 근사치"라고 정직하게 라벨한다.

### 1.5 HWP/HWPX가 가장 뾰족하다 — 다만 이미 주인이 있다

**수요 촉발**: 2026-05-18부터 행정기관 전자문서에 개방형 포맷(HWPX/ODF/PDF-A) 사용이
의무화됐다(행정업무 운영·혁신 규정 개정, 5-12 국무회의 의결). 2007년 ODF 표준은 강제력이
없어 사문화됐지만 이번은 다르다.

**기존 대안**: hwp2pdf.kr 등 온라인 변환기는 전부 서버 업로드(직접 확인). 한컴독스·폴라리스는
로그인 기반 클라우드. 한컴 뷰어는 데스크톱 설치. pyhwp는 2020년 이후 실질 중단, hwp.js는
2025-01 이후 정체.

**그리고 rhwp가 있다**: `edwardkim/rhwp`, 3,648★, MIT, **2026-03-27 생성, 오늘도 커밋**.
Rust+WASM, HWP5/HWPX/HML 파싱, SVG·PNG·PDF 출력 주장. `@rhwp/core`(파서·렌더러) +
`@rhwp/editor`(에디터 UI) npm 배포. **이미 GitHub Pages에 데모가 있다**(edwardkim.github.io/rhwp).

솔직히: 우리가 "HWP 뷰어+변환기"만 만들면 그건 rhwp 데모의 재포장이다.

### 1.6 로컬 실증 — rhwp WASM에 실제 결함이 있다

우리 행정학개론 문제지로 직접 측정했다.

| 경로 | 파싱 | 페이지 SVG | 결과 |
|---|---|---|---|
| rhwp CLI v0.7.2 (네이티브) | — | — | **정상**. 2단 조판·박스·원문자 보존. 단 쪽번호 빈칸 |
| `@rhwp/core` 0.7.19 (WASM) | 60ms | 52ms | 우측 단 텍스트 잘림, 박스가 본문과 겹침. 쪽번호는 채움 |
| `@rhwp/core` 0.8.2 (WASM) | 60ms | 52ms | 0.7.19와 동일하게 깨짐 |

WASM 두 버전이 픽셀 단위로 같고 CLI만 다르다. 즉 버전 회귀가 아니라 **CLI와 WASM 렌더 경로의
분기**로 보인다. 다만 CLI는 0.7.2, WASM은 0.7.11 이상이라 버전 차이가 완전히 배제되진 않았다.
확정하려면 최신 태그로 CLI를 빌드해 같은 파일을 렌더해야 한다(미완, 아래 P0에 넣음).

rhwp README도 한컴 PDF를 기준 정답으로 삼지 않는다고 스스로 밝히고 있다. **즉 이 생태계에는
아직 렌더 충실도 기준선이 없다.** 이게 우리가 들어갈 틈이다.

## 2. 그래서 무엇을 만드는가

### 2.1 제품 정의

> **한국에서 실제로 돌아다니는 문서 뭉치(HWP/HWPX, PDF, 이미지)를 한 곳에서 열고, 보고,
> 가볍게 고치고, 서로 변환하는 도구. 파일은 네트워크로 나가지 않는다.**

경쟁자들이 못 하는 조합이 이거다. BentoPDF·PDFCraft는 PDF만, 영어권. rhwp는 HWP만.
Squoosh는 이미지만. **한국 사용자의 실제 폴더에는 셋이 섞여 있다.**

### 2.2 차별점 3개

1. **무업로드가 증명 가능**: 네트워크 탭에 요청이 0인 걸 UI에서 직접 보여준다. 오프라인
   모드로 완전히 작동한다(PWA). "지웁니다"가 아니라 "안 보냅니다".
2. **HWP를 제대로 다루는 유일한 통합 도구**: 정부 HWPX 의무화 타이밍과 정확히 맞는다.
3. **속도**: 파싱 60ms를 측정했다. 업로드 왕복이 없으니 구조적으로 빠르다. 이걸 UI에서
   숫자로 보여준다(파일 열림까지 ms 표시).

### 2.3 범위 (v1)

**넣는다**
- 뷰어: HWP/HWPX, PDF, 이미지(HEIC 포함), 텍스트/마크다운
- 변환: HWP/HWPX → PDF·PNG / PDF ↔ 이미지 / 이미지 포맷 상호변환·리사이즈·압축 / HEIC → JPEG
- PDF 편집: 병합·분할·회전·페이지 삭제·순서 변경
- 가벼운 문서 편집: rhwp 편집 API 범위 내 텍스트 수정 후 HWP/HWPX 재저장

**뺀다 (v1)**
- Office(docx/pptx) 변환 — 깨끗한 경로 없음
- 영상·오디오 — ffmpeg.wasm 실측 미검증(리서치 실패), 별도 판단 필요
- 클라우드 저장·계정 — 무업로드 정체성과 충돌

## 3. 아키텍처

```
Cloudflare Pages (정적)
  └ _headers: COOP/COEP  → SharedArrayBuffer 확보 (영상 확장 대비)
  └ Service Worker (PWA, 완전 오프라인)
       ├ @rhwp/core        WASM 7.2MB (gzip 2.7MB)  HWP/HWPX
       ├ pdf.js            PDF 렌더
       ├ pdf-lib + fontkit PDF 조작 (CJK는 폰트 서브셋 필수)
       ├ libheif-wasm      HEIC 디코드
       ├ @jsquash/*        WebP·AVIF 인코드 (Safari가 네이티브 미지원)
       └ Canvas API        기본 이미지 변환 (의존성 0)
```

**지연 로딩이 핵심**: WASM을 전부 선로드하면 첫 화면이 죽는다. 파일을 떨어뜨린 순간
확장자를 보고 필요한 모듈만 가져온다. 초기 번들은 앱 셸만.

**대용량**: `Blob.stream()` 청크 처리. iOS는 파일 크기 가드 + 경고.

**폰트**: pdf-lib 기본 폰트는 한글이 물음표로 나온다. Noto Sans KR 서브셋 임베딩 필수.

## 4. UI 방향

Refero 로컬 라이브러리에서 4개 레퍼런스를 뽑았고, 그중 **Getburnt(에디토리얼 모노크롬)**를
기준으로 잡는다. 근거: 도구인데 문서를 다루므로 "종이" 질감이 제품 의미와 맞고, 색을 아껴야
문서 내용이 주인공이 된다.

- 팔레트: 따뜻한 종이 흰색 + 잉크 블랙 + 회색 1단계. 강조색은 **단 하나**, 무업로드 상태 표시에만.
- 타이포: 디스플레이 세리프(제목) + 산세리프(UI) 페어링. 한글은 Pretendard.
- 레이아웃: 좌측 파일 트레이 / 중앙 캔버스 / 우측 작업 패널. 베이스는 드래그앤드롭 전체 화면.
- 금지: 기본 카드 그리드, 그라디언트 블롭 히어로, 균일 패딩, `transition: all`.
- 상태 8종(기본/호버/액티브/포커스/비활성/로딩/에러/성공) 전부 정의.
- 시그니처 요소: **네트워크 0 뱃지** — 세션 동안 나간 요청 수를 실시간 0으로 표시. 이게
  제품의 주장을 UI 자체가 증명하는 장치다.

준수: `~/.claude/rules/ecc/web/design-quality.md`(anti-template, 필수 품질 4개 이상),
`performance.md`(마이크로사이트 JS 80kb 예산 — WASM은 지연 로딩이라 별도 계산).

## 5. 단계

### P0 — 사실 확정 (반나절)
1. rhwp 최신 태그로 CLI 빌드 → 같은 파일 렌더 → CLI/WASM 분기인지 버전 회귀인지 확정.
2. 확정되면 **재현 케이스와 함께 rhwp에 이슈 제출**. 이게 관계의 시작점이자, 우리가 이
   생태계에 실제로 기여했다는 증거가 된다.
3. HWP/HWPX 실문서 20~30개로 충실도 코퍼스 구성(공문서·시험지·표 많은 문서·수식 포함).
   **완료 (25개, 실문서만).** 방법론·축별 개수·실측 수치·NOT MEASURED 항목은
   `docs/fidelity/README.md` 참고. 수식 포함 실문서는 0건으로 확인됨(자동 열거 API 부재 +
   후보군 수동 검토 모두 못 찾음, 대체하지 않고 정직 표기).

### P1 — 뷰어 스파이크 (2~3일)
Cloudflare Pages에 최소 뷰어. HWP + PDF + 이미지 드롭 → 표시. 지연 로딩·오프라인 확인.
iOS Safari 실기기에서 메모리 한계 실측.

### P2 — 변환 (3~4일)
HWP → PDF, PDF ↔ 이미지, 이미지 상호변환. 각 변환에 결정론 검증(페이지 수·텍스트 추출 대조).

### P3 — 편집 (3~4일)
PDF 병합·분할·회전. rhwp 편집 API로 텍스트 수정 + 재저장.

### P4 — 마감
PWA, 네트워크 0 뱃지, 접근성(키보드·대비), 4개 브레이크포인트 시각 회귀.

## 6. 리스크와 반대 논거

**가장 강한 반대**: rhwp가 이미 뷰어·에디터·데모를 다 갖고 있고 매일 커밋된다. 우리가
만드는 건 그 위의 얇은 껍데기이고, rhwp가 자기 데모를 조금만 다듬으면 우리 가치는 0이 된다.

이에 대한 답은 하나뿐이다. **HWP 단일 포맷 도구를 만들지 않는 것.** 가치는 "HWP를 연다"가
아니라 "섞여 있는 문서 뭉치를 한 곳에서, 안 올리고 처리한다"에 있어야 한다. 그 조합은 아직
아무도 안 만들었다. 만약 범위가 HWP로 좁혀지면 그때는 만들지 말고 rhwp에 기여하는 게 맞다.

**두 번째 리스크**: 렌더 충실도. 한컴 원본과 다르게 나오면 공문서 용도로는 못 쓴다. P0의
충실도 코퍼스가 이걸 막는 유일한 장치다. 완벽하지 않으면 "참고용" 라벨을 붙이고 정직하게 판다.

**세 번째**: SEO로는 못 이긴다. iLovePDF는 월 1억 건대 트래픽 규모다(2차 출처, 미검증).
유입은 GitHub·HN·개발자 커뮤니티로 간다. BentoPDF·PDFCraft가 정확히 그렇게 컸다.

## 7. 미검증 항목 (정직 표기)

- 영상/GIF 수요 순위와 ffmpeg.wasm 번들 크기·속도 — 리서치 에이전트 토큰 소진으로 실패.
- iLovePDF 트래픽·매출 — 2차 출처만 존재.
- "convert X to Y" 키워드 난이도 — 키워드 도구 접근 불가로 정성 추론.
- rhwp CLI/WASM 분기 원인 — P0에서 확정 예정.
- rhwp의 "byte-reproducible PDF" 주장 — 자기 보고, 미검증.
